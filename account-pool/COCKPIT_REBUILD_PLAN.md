# 号池管理系统重做计划书（CPAMC 对齐版）

## 1. 文档状态与目标

本文是号池系统重做的实施计划，当前处于方案审核阶段，不包含代码重构、生产数据删除或部署操作

目标是在 LiteLLM 管理台内建设一个以“号池卡片”为中心的管理系统。管理员可以按供应商创建任意数量的卡片，为每张卡片配置多个凭据、模型、路由、配额、代理和运行参数，并为每张卡片生成一个独立 Key 交给 NewAPI 使用

NewAPI 继续负责下游用户、下游 Key、用户权限、预算和限流。LiteLLM 号池负责卡片 Key 校验、卡片内凭据选择、并发、配额、冷却、故障切换、会话粘性和上游转发

快速开始不纳入本次重做。本机 Codex 或 Cursor 的多开、窗口和 WSL 管理属于桌面端项目，不塞进 Linux 服务端号池

## 2. 参考界面与核实结论

本次以本机 `http://localhost:8317/management.html` 的 CPAMC 管理中心为第一参考，已看到的版本信息是 CPAMC `v1.22.15`，页面品牌为 CLI Proxy API Management Center

已核实的侧栏顺序如下

| 分组 | 页面 |
| --- | --- |
| 运行 | 仪表盘、快速开始 |
| 网关 | AI 提供商、认证文件、OAuth 登录 |
| 观测 | 配额管理、日志查看 |
| 控制 | 配置面板、插件管理、插件商店、中心信息 |

号池页面会把快速开始排除，并将其余页面放入号池模块的横向导航。桌面宽屏使用横向标签，窄屏使用可滚动标签或下拉菜单，页面地址仍保持可直接打开和刷新

参考页面的实际能力包括供应商家族选择、同一供应商多实例创建、多个 API Key 条目、每 Key 代理 URL 和权重、请求头、自定义模型、OAuth、配额窗口、结构化日志、59 项配置、插件目录和插件商城

当前参考实例没有凭据和模型，所以空状态、健康度和流量数字没有被当作真实运行数据。日志页提示必须先开启文件日志，插件商城因本机代理连接失败没有取得注册表内容，这两项在实施时需要单独做真实环境验收

## 3. 当前实现与重做原因

当前号池已经具备环境生命周期、OAuth 授权、卡片 Key、账号路由、并发租约、会话粘性、冷却、故障切换、结构化请求日志、配额快照、批量任务和 Clash 代理网关。这些能力继续复用，避免重新实现已经通过测试的底层行为

当前模型把 `EnvironmentRecord` 同时当作账号、卡片和运行环境，策略通过 `account_ids` 绑定同渠道同供应商的其他环境。它不适合表达“一个供应商创建多张命名卡片”和“一个卡片内有多个 API Key 或 OAuth 凭据”

当前前端仍以账号环境列表为中心，FreeBuff2API 贯穿渠道枚举、供应商枚举、Compose、镜像、测试和文案。它会把新系统限制在旧渠道模型内，也无法自然复刻参考页面的供应商实例和凭据条目

当前策略能力清单把 identity、websocket、debug 标记为暂不支持，把 desktop_compact 标为桌面端。重做后每个字段都必须显示实际作用范围，不能保存后伪装成已生效

## 4. 目标边界与职责

```text
NewAPI 下游用户和 Key
        -> 卡片 Key
LiteLLM 号池网关
        -> 卡片候选过滤、模型权限、配额、并发、会话和故障切换
卡片内凭据
        -> 供应商适配器或隔离的 CLIProxyAPI 运行环境
上游模型服务
```

控制面保存卡片、凭据元数据、策略、期望运行状态、统计索引和审计事件。数据面只接收公共模型请求并在请求级执行卡片策略。Manager 负责容器和运行环境生命周期，不承担公共模型网关职责

每个账号运行环境继续使用不可变 UUID、独立 Compose 项目、独立数据卷和独立网络，不发布宿主机端口。Docker Socket 只通过 Manager 专用的严格校验 Socket Proxy 使用，LiteLLM 公共进程不直接接触 Docker Socket

请求入口代理和上游出站代理是两个字段。卡片的出站代理只能从已登记的代理档案或网关列表选择，不能把下游请求中的代理参数传入运行环境

## 5. 新的数据模型

### 5.1 供应商家族、卡片、凭据和运行环境

```text
ProviderFamily 供应商家族
  -> ProviderInstance 供应商实例，也就是号池卡片
       -> CardCredential 卡片凭据，可有多个
            -> RuntimeEnvironment 需要隔离时的运行环境，可有一个或多个
       -> CardPolicy 卡片路由和协议策略
       -> CardKey 卡片对外 Key
```

| 对象 | 作用 | 关键字段 |
| --- | --- | --- |
| ProviderFamily | 静态供应商能力目录和表单模板 | `kind`、显示名、认证方式、能力清单、默认模型策略 |
| ProviderInstance | 用户创建的命名号池卡片 | `id`、`name`、`family`、`enabled`、状态、标签、分组、更新时间 |
| CardCredential | 卡片内一个 API Key、OAuth 文件或服务账号 | 加密密钥引用、状态、权重、优先级、备用标志、代理绑定、模型和配额快照 |
| RuntimeEnvironment | 需要隔离的 CLIProxyAPI 或适配器实例 | 不可变环境 ID、镜像版本、期望状态、观测状态、运行配置版本 |
| CardPolicy | 卡片级请求行为 | 路由、模型、配额、重试、协议、客户端准入、供应商扩展配置 |
| CardKey | NewAPI 使用的卡片入口 | Key 哈希、版本、撤销时间、最近使用时间、模型和卡片作用域 |
| RequestEvent | 脱敏请求审计和统计 | 卡片、凭据、模型、尝试序号、状态码、Token、耗时、路由原因、错误分类 |

卡片是用户可见的号池单位，凭据是卡片内可参与路由的成员，运行环境是承载某个凭据的执行单位。OpenAI 兼容卡片可以直接保存多个上游 Key，OAuth 供应商通常是一份授权文件对应一个隔离运行环境。这样既能支持一个供应商创建多张卡片，也不会把一个卡片的所有凭据错误地合并成一个账号

### 5.2 供应商家族目录

首版目录沿用参考页面的家族入口，同时由后端能力矩阵控制是否可创建和可执行

| 家族 | 首版入口 | 认证方式 | 首版执行策略 |
| --- | --- | --- | --- |
| OpenAI 兼容 | 可创建多个实例 | Base URL、一个或多个 API Key | 直接上游或受控适配器，完整支持模型、权重、代理、请求头和自定义模型 |
| Codex | 可创建 | OAuth、授权文件 | 复用 CLIProxyAPI Codex 适配器，支持授权、模型发现、额度和路由 |
| Claude | 可创建 | OAuth、授权文件或供应商 Key | 复用现有 Claude 适配器，供应商特定 Header 走能力矩阵 |
| Antigravity | 可创建 | OAuth、授权文件 | 复用现有适配器，签名缓存和敏感词配置按供应商作用域执行 |
| Kimi | 可创建 | 设备授权或授权文件 | 复用 Kimi 设备授权和额度适配器 |
| xAI | 可创建 | OAuth 或 API Key | 复用现有 xAI 适配器，未支持字段显示不可执行原因 |
| Gemini | 展示家族并保留扩展点 | 供应商原生认证 | 没有对应可靠适配器前不能伪装成可用，创建按钮显示需要适配器 |
| Vertex | 展示家族并保留扩展点 | 服务账号 JSON、区域 | 先实现 JSON 导入和安全存储，再接入模型请求和额度适配器 |
| Interactions API | 展示家族并保留扩展点 | 供应商原生认证 | 以独立协议适配器实现，不把 OpenAI 请求字段直接套用 |

家族目录是模板，不是账号。点击“OpenAI 兼容”立即进入创建实例表单，保存后列表显示该家族的实例数量。再次点击可以继续创建，不覆盖已有实例

### 5.3 卡片 Key 与 NewAPI

一张卡片默认有一个有效的 `cpk_` Key，支持创建、撤销、重置、复制一次性明文和查看脱敏状态。Key 只绑定卡片，不绑定单个凭据，路由由卡片策略决定

NewAPI 保存卡片 Key，并把卡片对应的 `/v1/models` 模型目录配置到下游渠道。卡片 Key 不能访问管理接口、Manager、插件接口或其他卡片。下游额度和用户权限继续由 NewAPI 管理，号池不重复建设用户体系

## 7. 仪表盘设计

### 7.1 顶部汇总

默认统计范围为最近 24 小时，支持 1 小时、24 小时、7 天和 30 天。所有数字必须从请求事件和凭据快照计算，不能由卡片数量推断流量

| 指标 | 定义 |
| --- | --- |
| 卡片总数 | 未处于删除完成状态的卡片数量 |
| 启用卡片 | `enabled=true` 且没有手动冷却的卡片数量 |
| 成功率 | 成功请求数除以已完成请求数，未完成请求不进入分母 |
| 故障数 | 进入错误状态的请求数，按请求计数，重试尝试另记 |
| 已处理请求 | 统计范围内进入号池网关的请求数 |
| 总流量 | 请求和响应字节数之和，同时显示输入/输出 Token |
| 健康凭据 | 最近健康检查成功且可路由的凭据数 |
| 模型数 | 当前所有卡片启用模型的去重数量 |

成功率、故障数和总流量放在首屏最上方。下方增加 10 分钟桶趋势、供应商家族横向对比、卡片健康分布、最近错误和运行配置摘要

### 7.2 供应商分组卡片

卡片按 `ProviderFamily` 分组，每组显示家族名称、实例数量、启用数量、家族成功率和家族流量。组内卡片使用响应式网格

每张卡片必须显示以下内容

| 区域 | 内容 |
| --- | --- |
| 标题 | 用户自定义名称、供应商家族、启停开关、状态徽章 |
| 请求 | 已处理请求数、成功率、最近请求时间 |
| 模型 | 最多显示三个模型，多余模型显示 `+N`，鼠标悬停显示完整列表 |
| 健康度 | 卡片健康百分比、可用凭据数/总凭据数、最近检查时间 |
| 配额 | 剩余比例最低窗口、重置时间、配额快照年龄 |
| 运行配置 | 路由策略、并发上限、重试次数、代理名称、运行版本 |
| 错误 | 最近一次错误分类和时间，敏感信息脱敏 |
| 操作 | 配置、卡片 Key、授权、刷新额度、查看日志、删除 |

双击卡片是桌面快捷方式，显式“配置”按钮必须保留以支持键盘、移动端和无障碍操作。双击打开的是该卡片详情，不打开全局设置

### 7.3 数据接口

首屏使用一个聚合接口返回汇总、家族分组、卡片摘要和时间范围，卡片详情和日志使用分页接口。接口返回 `data_freshness` 和 `partial` 标志，任何指标无法取得时显示未知或部分数据，不显示 0 代替未知

## 8. AI 提供商页面

页面上半部复刻参考页面的家族选择卡片，下半部显示实例列表

家族区显示家族图标、名称、当前实例数、启用数和“新建”。点击家族直接打开该家族的新建表单，不要求先进入一个空列表页。列表支持刷新、搜索、按名称/更新时间/请求数/健康度排序、家族筛选和模型筛选

OpenAI 兼容新建表单至少包含以下字段

| 分组 | 字段 |
| --- | --- |
| 基础 | 名称、服务地址、模型前缀、优先级、测试模型 |
| 状态 | 启用、停用条目、禁用冷却调度 |
| 凭据 | 多个 API Key 条目、添加、展开、收起、移除、单 Key 测试、全部测试 |
| 凭据参数 | 每 Key 的代理 URL、调度权重、优先级、备用标志 |
| 请求头 | 可折叠的自定义请求头，敏感值只写入密钥存储 |
| 模型 | 可折叠的自定义模型、别名、输入/输出能力和图片能力 |
| 完成 | 取消、创建、创建后进入卡片详情并开始模型发现 |

同类实例创建不能复用前一个实例的密钥明文，也不能因名称相同而覆盖旧卡片。名称是展示字段，不能用作 Compose 项目名、路径或路由身份

OAuth 型家族沿用同一页面结构，但凭据区改为授权状态、授权时间、重新授权和授权文件关联。供应商特有字段由家族能力描述驱动，不能把 Codex 字段硬塞给 Claude、Kimi 或 xAI

## 9. 认证文件、OAuth、配额和日志

### 9.1 认证文件

认证文件页显示总凭据数、启用数、问题数、刷新、上传、供应商筛选、卡片筛选、搜索、状态筛选、排序和安全删除。列表只返回文件名、家族、卡片、状态、模型数、最后刷新时间和错误摘要，不返回 access token、refresh token、完整 JSON 或代理密码

OAuth 模型禁用和模型别名保留为二级面板，修改后明确显示影响的卡片和凭据数量。批量删除要求二次确认并先从候选路由摘除

### 9.2 OAuth 登录

保留 Kimi 设备授权、Codex、Claude、Antigravity、xAI OAuth 开始登录和 Vertex 服务账号 JSON 导入。每次授权都关联目标卡片和一次性 state，state 必须有签名、过期时间、消费时间和目标卡片 ID

授权回调只能消费一次。过期、重复、环境不匹配、签名不匹配和已经删除的卡片必须返回稳定错误，不能把回调转发给其他卡片。授权完成后依次执行凭据安全存储、运行环境配置、模型发现和健康检查，全部通过后才进入 ready

### 9.3 配额管理

保留参考页面的家族标签和刷新全部按钮，增加卡片、凭据、模型筛选。每个配额窗口显示已用比例、剩余比例、窗口长度、重置时间、观测时间、快照年龄和来源

上游百分比配额和本地 Token 预算分开显示。Token 预算只表示本地账本的原子预留和结算，不把百分比额度换算成 Token，也不使用公共价格表伪造金额

### 9.4 日志查看

复刻日志内容、错误请求、关键字搜索、结构化筛选、原始日志、自动刷新、下载、清空和全屏布局。号池扩展以下筛选

| 筛选 | 作用 |
| --- | --- |
| 卡片 | 定位某个号池实例 |
| 凭据 | 定位某个 API Key 或 OAuth 文件 |
| 供应商和模型 | 定位协议或模型问题 |
| 请求 ID | 查看一次请求的全部尝试链 |
| 路由原因 | 查看优先级、配额、粘性、重试切号等原因 |
| 错误分类 | 认证、限流、超时、连接、无效请求、上游和配置 |

日志事件只保存脱敏摘要、哈希或内部 ID，禁止保存完整 Authorization、Cookie、refresh token、代理凭据和完整生成配置

## 10. 配置面板的作用域拆分

### 10.1 继承和覆盖规则

配置生效顺序为：系统硬限制、全局设置、供应商家族默认值、卡片覆盖、凭据覆盖、请求级准入条件。卡片页面显示每个字段来自哪一层，并提供“恢复继承”操作

全局设置页提供三种保存范围：仅保存默认值、应用到选定卡片、应用到全部卡片。批量应用先生成差异预览和任务 ID，再异步执行，保留每张卡片的旧版本以便回滚。全局修改不能覆盖卡片明确锁定的字段，除非管理员先解除锁定

### 10.2 单卡片设置审核清单

以下是双击卡片后可编辑的首版清单。表中的“执行位置”是最终改变请求行为的地方，不是表单保存位置

| 类别 | 单卡片字段 | 默认行为 | 执行位置 | 运行时状态 |

## 11. 代理设置设计

代理设置直接复用现有 `ProxyProfileRepository`、Clash 网关端口和节点控制，不另造一套代理数据库。统一目录提供代理档案名称、协议、脱敏地址、来源、健康状态和最近测速时间

卡片配置的代理下拉框至少包含：默认网关、现有代理档案、Clash 网关端口。代理凭据只保存在服务端密钥存储，列表和卡片摘要只显示名称与协议

Clash 网关节点切换是共享操作。如果多个卡片使用同一端口，页面必须显示受影响卡片数量，并在切换前提示这是共享出口变化。卡片选择独立代理档案时，不应因其他卡片切换 Clash 节点而改变

代理地址必须通过严格 URL 校验，禁止 `file`、内网管理协议和带未编码控制字符的地址。运行环境只接受已登记的 profile ID 或网关 ID，不接受前端直接提交任意代理 URL

## 12. 插件管理和商城

参考页面的“标准动态库插件加载”不能直接等同于 LiteLLM Python 进程可加载的 ABI。重做采用兼容层

1. 插件管理页和商城页先完整复刻发现、搜索、安装状态、启停、配置入口、更新、重试和回滚流程
2. 每个插件必须有 manifest，声明运行时版本、入口类型、能力范围、所需配置、供应商范围和卡片范围
3. 下载前校验 registry 来源、版本、SHA-256 和签名信息。私有源认证只保存环境变量名，不保存真实 token
4. 插件在隔离的插件运行器或专用 sidecar 中执行，通过窄接口访问模型请求事件和卡片策略，不能直接读取 LiteLLM 进程内全部凭据
5. 不符合 LiteLLM 运行时或 ABI 的 CPA 动态库显示为“不兼容”，不能伪装成已安装生效
6. 安装、更新、卸载和启停都是幂等任务，保留旧版本以便回滚。插件全局开关关闭时，实例页明确显示“发现但未生效”

商城网络不可用时使用已缓存注册表和清晰错误状态，不绕过认证下载未知文件，不把用户代理故障改成成功状态。安装插件前显示其能读取的字段和可能影响的卡片范围

## 13. FreeBuff 移除和既有数据处理

FreeBuff 不再出现在新建渠道、供应商家族、卡片筛选、配置能力和文档中。移除分为停用、迁移、清理三个阶段，计划审核通过前不删除现有生产卷和数据库记录

### 13.1 停用

- 发布兼容版本后禁止创建 `freebuff2api` 和 `freebuff` 新记录
- 现有 FreeBuff 卡片标记为 `migration_required`，从默认路由摘除，不静默转成其他供应商
- 页面提供导出非敏感元数据、查看卡片 Key 引用、停止运行环境和删除的明确操作

### 13.2 迁移

- 先备份号池数据库、Manager 数据卷、FreeBuff 数据卷和 Compose 清单
- 只迁移卡片名称、标签、模型别名、统计摘要和审计元数据，不迁移或展示完整 Token
- 能映射到 OpenAI 兼容或其他受支持家族的记录由管理员创建新卡片并重新导入凭据，禁止自动猜测上游身份
- 迁移命令必须可重复执行，有报告、有失败项和回滚点。大表迁移在独立维护命令中执行，数据库启动迁移只增加结构，不重写请求记录

### 13.3 清理

确认所有 FreeBuff 卡片已停用、导出或删除后，移除 FreeBuff 渠道实现、供应商枚举、Compose 分支、镜像目录、环境变量、注册表入口、前端文案、类型声明和测试

清理后对旧 API 请求返回明确的“渠道已移除”，不把旧数据解析成 OpenAI。最终验收包括仓库搜索无运行时 FreeBuff 引用、镜像构建不再带 FreeBuff、数据库没有仍可路由的 FreeBuff 卡片

## 14. API 和版本契约

保留现有管理代理的鉴权方式，新增资源使用版本字段、ETag 或等价的乐观并发控制和幂等操作 ID。建议的接口分组如下

| 资源 | 主要接口 |
| --- | --- |
| 供应商目录 | `GET /account_pool/provider-families` |
| 卡片 | `GET/POST /account_pool/cards`、`GET/PUT/DELETE /account_pool/cards/{id}` |
| 卡片配置 | `GET/PUT /account_pool/cards/{id}/policy` |
| 凭据 | `GET/POST/PUT/DELETE /account_pool/cards/{id}/credentials` |
| OAuth | `POST /account_pool/cards/{id}/authorize`、回调和重新授权接口 |
| 卡片 Key | `GET/POST/PUT/DELETE /account_pool/cards/{id}/key` |
| 仪表盘 | `GET /account_pool/dashboard?range=24h` |
| 配额 | `GET /account_pool/quotas`、刷新任务接口 |
| 日志 | `GET /account_pool/logs`、`GET /account_pool/logs/{event_id}` |
| 全局配置 | `GET/PUT /account_pool/settings`、批量应用任务接口 |
| 代理 | 复用现有 profile、gateway、node、delay 接口并补充卡片绑定检查 |
| 插件 | `GET /account_pool/plugins`、启停、安装、更新、卸载和商城 registry 接口 |

旧的 `/account_pool/environments` 接口在迁移期间保留只读兼容层，返回卡片和凭据的投影视图。新前端不再直接把环境当作卡片写入。兼容层移除前完成数据迁移和客户端切换

所有接口再次执行管理员权限校验。公共模型网关只接受有效卡片 Key，不接受 Manager token 或管理 Key

## 15. 实施顺序

### 阶段 0：冻结契约和基线

- 锁定 ProviderFamily、Card、Credential、RuntimeEnvironment 的关系
- 记录当前数据库、卷、镜像和 FreeBuff 使用情况

### 阶段 1：领域模型和持久化

- 保留现有环境生命周期、租约、会话和删除检查点

退出条件：并发更新、删除重试、OAuth state 消费、密钥轮换和迁移命令测试通过

- 在 LiteLLM Dashboard 增加号池横向导航和权限入口

- 接入实时刷新、错误状态、部分数据和无权限状态

退出条件：使用静态夹具能完整展示多家族、多卡片、多模型和 `+N` 悬停列表，响应式布局和键盘操作通过

### 阶段 3：供应商实例、凭据和 OAuth

- 实现家族目录和 OpenAI 兼容多实例创建

- 实现模型发现、授权恢复、重新授权和凭据健康

退出条件：同一供应商连续创建多张卡片互不覆盖，每张卡片可以添加和删除多个凭据，授权失败不会污染其他卡片

### 阶段 4：卡片配置和全局配置

- 按本计划的清单完成卡片面板
- 重构配置面板为全局默认、家族默认、卡片覆盖、凭据覆盖
- 增加差异预览、恢复继承、批量应用、版本和生效状态
- 对 identity、WebSocket、debug、桌面 Compact 等当前缺口补齐实现或明确阻止保存

退出条件：每个可编辑字段都有执行位置和能力状态，修改卡片不会影响其他卡片，全局应用可预览、可回滚

### 阶段 5：配额、日志、代理和数据面

- 完成卡片、凭据、模型维度的配额窗口和刷新任务
- 接入卡片 Key、请求事件、重试链和路由原因日志
- 复用现有代理档案和 Clash 网关，增加卡片绑定和共享影响提示
- 把卡片策略真正接到网关候选过滤、并发、会话、冷却和故障切换

退出条件：一次请求能在日志中看到卡片、凭据、模型、尝试序号、路由原因和最终结果，配置修改能改变真实请求行为

### 阶段 6：插件兼容层和商城

- 实现 registry、manifest、校验、安装、更新、回滚、启停和配置字段
- 落地隔离插件运行器或 sidecar，禁止不兼容动态库进入 LiteLLM 进程
- 处理私有源认证、离线缓存、网络失败和插件权限展示

退出条件：安装一个受支持测试插件后能看到发现、安装、生效、停用和回滚全链路，未知或不兼容插件被拒绝

### 阶段 7：FreeBuff 清理和发布验收

- 完成旧卡片迁移报告和备份检查
- 删除 FreeBuff 运行时和前端入口
- 执行静态搜索、类型检查、镜像构建和数据库兼容检查
- 在真实 Docker、PostgreSQL、NewAPI、上游和代理环境完成端到端请求

退出条件：没有可路由的 FreeBuff 记录，NewAPI 能使用每张卡片 Key 请求模型，卡片策略、配额、代理、日志和插件操作均有运行时证据

- 所有保存操作有成功、失败、待对账和不支持状态

### 16.3 真实链路

1. 创建两个 OpenAI 兼容卡片，每张卡片添加两个凭据
2. 分别为卡片选择不同代理，验证出口和卡片摘要
3. 给每张卡片生成 Key，在 NewAPI 创建对应渠道
4. 使用卡片 Key 请求 `/v1/models` 和最小 Responses 或 Chat Completions 请求
5. 触发一次可重试错误，确认日志显示重试、切号、路由原因和最终结果
6. 修改卡片并发、模型和代理，确认只影响目标卡片
7. 修改全局默认并预览全部卡片差异，确认锁定覆盖字段不被改写
8. 刷新配额、制造冷却、等待恢复，确认健康度和候选列表同步
9. 安装、停用和回滚受支持插件，确认插件权限边界
10. 删除卡片，确认先摘路由、再清理运行环境、最后清理元数据和 Key

测试完成后必须保存接口响应、日志片段、容器和网络清单、NewAPI 请求结果及配置版本作为验收证据。没有 Docker、PostgreSQL、NewAPI、上游或代理的本地环境只能通过单元和集成测试，不能宣称端到端完成

## 17. 需要审核的关键选择

本计划建议按以下选择实施

1. “卡片”代表供应商实例和号池，多个 API Key 或 OAuth 凭据属于卡片成员，隔离运行环境属于凭据执行单位
2. OpenAI 兼容作为第一条完整闭环，Codex、Claude、Antigravity、Kimi、xAI 沿用已有适配器逐步接入，Gemini、Vertex、Interactions API 先显示目录和能力状态
3. 全局设置默认只影响新卡片，应用到已有卡片必须先预览并作为可回滚批量任务执行
4. 代理目录复用现有服务器数据，卡片只保存 profile ID 或网关 ID，不保存任意前端 URL
5. 插件商城先做真实安装生命周期和兼容校验，再通过隔离运行器提供插件执行，禁止把 CPA 动态库直接加载到 LiteLLM 进程
6. FreeBuff 先停用和迁移，确认备份及卡片引用后再移除代码、镜像和配置

以上选择确认后，再进入阶段 1 的数据库和 API 改造。确认前不删除 FreeBuff、不改现有生产卡片、不安装插件、不部署服务
