# 自动化上号

入口位于号池的“认证文件”之后，分为认证文件导入和 OAuth 上号。仅代理管理员可使用

认证文件每批最多 100 个 JSON，单文件最多 1 MiB，每批总计最多 8 MiB。选择对应供应商，预览有效、重复、无效项后提交。文件的 `type` 或 `provider` 必须与供应商一致。每个任务使用固定卡片 ID，失败重试和服务重启恢复复用原卡片。此流程不生成 OAuth 链接，不进入邮箱账号库存

新卡片使用当前全局默认并发和代理，运行设置仍通过现有全局配置同步机制生效。并发和代理遵循原有卡片配置规则，不新增自动覆盖用户设置的机制。认证信息、模型和配置验证成功后，按“供应商-套餐-账号”命名；套餐未知时使用“套餐待识别”

OAuth 首批支持 Outlook、Gmail、通用邮箱分类。账号文件使用 JSON 数组：

```json
[
  {
    "email": "you@example.com",
    "mailbox_password": "邮箱密码",
    "supplier_password": "可选的供应商密码"
  }
]
```

邮箱和供应商密码分别加密保存，列表不返回密码。管理员点击查看时读取，60 秒后隐藏，也支持复制。可生成建议随机密码；只有管理员在官方邮箱页面完成改密并确认后，才替换记录中的邮箱密码。个人 Outlook、Gmail 和未配置管理接口的通用邮箱尚不支持无人值守改密

准备好的账号可启动现有供应商 OAuth，授权链接、设备码和回调说明复用现有组件。登录、验证码及二次验证需人工接续。后台确认授权、模型及配置后更新任务状态，产生链接不代表成功。读取到的授权邮箱与库存邮箱不一致时停用该卡片并提示检查

每个供应商可以设置一个可用数量目标和可选模型。后台优先保留已就绪的账号，将排队、验证和等待授权计入处理中；数量不足时从已完成邮箱准备的库存排队。额度耗尽或模型冷却从可用统计中扣除，沿用现有配额和健康恢复机制。不会将认证文件卡片加入 OAuth 库存，不会自动重试过期授权，也不会覆盖手动停用。降低目标不会删除或停用已有卡片

后台每 5 秒处理一项排队任务，至少每 30 秒观察 OAuth 任务状态。任务锁与凭证归属锁隔离于推理链路。新建两张独立数据表 `account_pool_onboarding`、`account_pool_onboarding_targets`，不修改现有数据。镜像回退时旧版忽略这些表，任务停止，恢复新版本后继续；加密依赖原有 `ACCOUNT_POOL_SECRET_SEED`，需随现有密钥管理方式妥善保留

本次验证涵盖 29 项后端相关检查、9 项前端测试、新组件 TypeScript 和 ESLint 检查、浏览器页面与分页预览，以及隔离 PostgreSQL 数据库的插入去重、跨进程锁、加密读写和状态恢复。未使用真实新账号完成 OAuth 或认证文件导入，不代表所有供应商已完成线上端到端验证
