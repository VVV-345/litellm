# Unified deployment images

`Publish deployment images` is the product release entrypoint. The existing `CLIProxyAPI分支` and `codex/fix-*` push triggers remain enabled. For a manual run, the GitHub Actions workflow ref or branch dropdown must select `CLIProxyAPI分支`; `source_ref` selects only the source checkout, not the workflow code. Do not invoke the old default `litellm_internal_staging` workflow for this product. Run `gh workflow run publish-deployment-images.yml -R VVV-345/litellm --ref CLIProxyAPI分支 -f "source_ref=<full-40-character-commit>" -f version_bump=patch`, replacing the source value with the complete verified commit SHA. The default patch sequence is resolved from `deploy/VERSION` and successful immutable Git tags. `Publish adapted CLIProxyAPI image` delegates to the same four-component workflow and no longer writes the historical CLIProxyAPI package

All four components publish to `ghcr.io/vvv-345/litellm-cliproxyapi`. Their prefixes are `litellm`, `manager`, `browser-worker`, and `cliproxyapi`. Each component has `<component>-<commit10>`, `<component>-<version>-<commit10>`, and `<component>-<version>` tags. Existing tags are verified and never moved; mismatched existing content fails the run. A rebuild that changes an existing SHA manifest is rejected rather than silently replacing it

The quota, persistence, release compatibility, and UI gates run before builds. Native amd64 and arm64 builds publish by digest first. The exact published digests must pass architecture, product revision, and component-label checks plus the component probe: LiteLLM and Manager imports, a headless Chromium launch for browser-worker, or the authenticated managed-identity HTTP probe for CLIProxyAPI. Import probes do not replace production database, provider, or OAuth acceptance checks

CLIProxyAPI uses the fixed commit and verified patch hash in `account-pool/cliproxy-adapter/sources.json`. The existing `apply.py` checks the clean source checkout and patch hash before applying it. All images use the product repository and full LiteLLM commit in the OCI source/revision labels. `ai.zlia.component` distinguishes the shared package components. CLIProxyAPI additionally records `ai.zlia.source-revision`, `ai.zlia.patch-sha256`, and `ai.zlia.managed-identity-version=1`

Only after all eight platform probes pass does the workflow assemble the four SHA manifests. `deploy/release_manifest.py` requires all eight successful build receipts and all four double-platform manifest receipts. It produces the schema 2 `release-manifest-<version>-<commit10>` Actions artifact containing product identity, every manifest digest, platform build digests, source revision, patch hash, and managed-identity version. The same bytes are retained as the durable `release-manifest.json` asset on the immutable GitHub Release. An existing asset must match exactly and is never overwritten. This audit artifact is separate from the deployment worker's legacy two-business-service backup manifest

The version aliases use the recorded immutable digests. The Git success marker and durable GitHub Release are the final job, after aliases and summary succeed, so a failed build or gate does not advance the product version. A failed run can leave digest-only images or partial aliases; rerun the same source rather than replacing a published tag. If GitHub asset upload or release finalization fails after the Git tag was created, the product build succeeded but the release is incomplete; retry that same commit to finish the asset without changing the tag. Historical packages and tags are not cleaned up

Publishing does not deploy a server, enable the browser worker, update the release worker, or recreate account containers. Use the existing deployment backup, compatibility, and controlled-update gates for those operations
