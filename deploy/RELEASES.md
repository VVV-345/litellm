每次发布先执行 [统一更新操作手册](UPDATE_RUNBOOK.md) 的检查表；本文解释发布器、备份和恢复机制

入口在“号池 / 版本管理”，管理 LiteLLM 和号池 Manager 的配套镜像。CLIProxyAPI 上游更新仍在原来的上游同步页面

页面下拉框显示当前版本、备份版本和手写备注。完整 commit 可复制，备注和代码回退说明可编辑，保存时等待 5 秒再确认。应用等待 5 秒，删除等待 10 秒，等待结束后均须手动点击确认；确认 5 分钟后失效

## v1.7 ISP 订阅与代理链适配（2026-10-23）

按用户要求将产品版本系列设为 `v1.7`。版本标签只在配套镜像构建及发布门禁成功后由工作流创建；push 和构建结果不代表已在服务器部署，本轮不替换线上镜像、配置或数据。

保留既有 Clash 配置来源、机场节点、普通机场代理模式、手工 ISP 配置和账号卡片请求逻辑。ISP 链路由管理员明确指定机场前置；配置不完整时拒绝请求，不自动选择节点，也不绕过 ISP。已有 ISP 绑定升级后可能需要补选前置节点，再启用链式路由。

ISP Clash 订阅与节点、前置绑定、独立 ISP 链路探测和 API/Dashboard 管理增加精确 schema allowlist。订阅 URL 和下载目标校验公网 DNS 并固定连接解析结果，禁止重定向和超限读取。删除失败时恢复端口后补偿外键绑定。批量探测包含手工 ISP 和支持直测的订阅节点；无法完整表达的协议或传输配置返回明确错误，仍需通过绑定端口检测完整链路。发布器另补回归，确保新增 schema 检查读取成对镜像的 Manager 源码和 LiteLLM Prisma。

2026-10-25 补齐订阅检测结果表 `account_pool_isp_subscription_probe_results` 的精确新增规则，同时保留旧 schema 组合、Prisma 一致性、禁止删除及拒绝未审阅变更的检查。旧 v1.7 发布器没有这条规则，仅发布业务镜像不能让它自动识别；部署前须按 `UPDATE_RUNBOOK.md` 第 5 节先更新独立 release-worker，再执行带备份的业务升级，不关闭兼容性检查。此修复不修改现有表或业务数据，也不代表已部署

同轮修复订阅节点本地改名后刷新丢失身份的问题：使用加密连接配置中保留的订阅原名识别节点，按 ID 停用源中缺失的节点，保留本地显示名和端口绑定。连接配置仍随订阅更新，启用状态仍由刷新重置。已有重复来源身份或新来源名与本地显示名冲突时拒绝刷新，保留原目录和绑定，须先人工处理冲突；不自动合并节点或换绑端口。订阅提供方改名不等同于本地改名，仍按源节点移除及新增处理

本地 Manager/真实临时 PostgreSQL、LiteLLM、Dashboard 和发布门禁的测试结果记录在 `account-pool/docs/isp-subscription-v1.7-verification.md`。严格 Manager 类型检查仍有历史及本轮范围内诊断，未作为通过项；真实 ISP、机场、供应商模型请求和生产部署均未验收。添加表只通过精确 DDL allowlist，不构成对全部 Manager 源码的摘要锁定。

## v1.6 本地修复（2026-10-16）

按用户要求将产品版本设为 `v1.6`，本轮只保存本地提交，不 push、不部署、不提前创建成功版本标签

Responses 续聊在授权卡片范围内恢复可见历史，保留同加密边界的推理内容，移除跨边界密文。恢复层共用截止时间、次数预算及已失败卡片集合，迁移后的网关不再叠加重试；已输出流和无法安全重放的请求保持原来的禁止重放边界。卡片新增连接测试，只请求选定卡片，不换卡，不把 HTTP 200 或不完整输出视为成功

ISP 凭据仍写入加密字段，API 只返回 `credentials_configured`。编辑时空值或纯空白保留旧值，非空密码保留原始空格，`clear_credentials` 显式清空。无效请求和数据库失败不回显凭据。最近探测结果写入 `account_pool_isp_probe_results`，失败覆盖旧成功结果，乱序返回不能覆盖更新的记录；重启读取同一数据库后恢复，删除 ISP 时级联删除探测记录。卡片标题显示延迟，24 小时后标为过期；列表或探测请求失败时显示错误并保留已有记录

新增表只执行 schema DDL。兼容门禁仅增加该表的精确已审阅组合，不开放任意 schema 变更。后续发布仍须 LiteLLM、Manager 配套构建，并按更新操作手册执行备份和线上验收。本轮本地测试和临时 PostgreSQL 验证不代表生产 ISP 或真实模型调用已经验收

## 成功构建递增版本（2026-10-15）

`deploy/VERSION` 保存产品系列基线。流水线从成功发布后创建的 `v<版本>-<提交前10位>` Git 标签计算新版本。默认 `patch` 按配置系列递增；手动运行时选择 `version_bump=minor` 或 `major` 时提升相应版本段。同一已发布提交重跑沿用原版本，不占新号

整个发布工作流共用并发组，避免两个正在运行的发布分配同一版本。构建失败不创建成功标签，不消耗编号。所有架构构建和 manifest 检查通过后才记录成功标签，随后发布易读的 `v1.2.1` 等镜像别名。别名发布失败可重跑原提交补齐，SHA/digest 仍为部署身份，不修改 LiteLLM 上游包版本，不移动已有 Git 标签

下面的 v1.1 规则和构建记录仅保留为历史；新的递增规则替代固定系列规则，备份、兼容性、健康检查与回滚门禁不变

## v1.1 固定版本系列（2026-10-13）

- 本项目产品版本以 `deploy/VERSION` 为唯一来源，固定 `v1.1`；只有用户明确要求才能改版本号。这不是 LiteLLM 上游包版本，不改上游 `pyproject.toml` 的版本。
- 本次发布 Git 标签为 `v1.1`；后续发布使用 `v1.1-<提交前10位>`，不移动或强推已有标签。阶段提交保留 conventional commit 格式，主题注明 `v1.1`。
- 镜像同时发布原有 `<提交前10位>` 和 `v1.1-<提交前10位>`，OCI version 为 `v1.1`、revision 为完整提交。自动更新继续按 HEAD、成功 workflow 和 SHA/digest 核对，不改成追随可变版本标签。
- `publish-deployment-images.yml` 的构建阶段只向 GHCR 推送按 digest 寻址的无标签镜像，并上传每个镜像架构的 digest 清单。额度切换、数据库兼容与备份/恢复测试、配置持久化、自动拉取/替换失败重试及页面开关测试必须先通过；全部 amd64/arm64 构建成功后，manifest job 才据 digest 发布 GHCR 正式标签，全部 manifest 检查通过后才创建 `v1.1-<提交前10位>` Git tag。
- 构建失败时不会创建 GHCR 标签或 Git tag；失败任务可能留下无标签的 digest 镜像对象，但它不是可部署版本。正式标签或 Git tag 已存在且指向其他提交时，流水线失败，不移动或强推它们。固定 `v1.1` Git tag 保持不动。
- 发布兼容回归由 `test_release_runtime.py` 和 `test_release_database.py` 覆盖 schema 例外、额外结构拒绝、双库快照及失败恢复；`test_release_workflow.py` 检查 YAML 依赖关系，确保正式标签步骤位于构建/manifest 门禁之后。
- `v1.1-*` 镜像构建标签不由最近 20 项清理策略删除，保留回溯能力；存储清理由管理员另行规划。
- push 会触发 CI；启用自动更新的服务器可能随后部署。push/构建成功不等于服务器替换成功，仍按 UPDATE_RUNBOOK 记录实际运行 revision 和回滚门禁。
- 发布器默认继续执行兼容性门禁。只有在确认接受数据读写不兼容风险后，才可在 release-worker 的 Compose 环境中设置 `ACCOUNT_POOL_RELEASE_SKIP_COMPATIBILITY_CHECKS=true`；该设置会跳过手动和自动 deploy、apply 的兼容性阻断，不跳过镜像完整性、人工确认、数据库备份、健康检查或失败恢复，确认响应和任务日志会标记已绕过。打开后自动更新也可能部署不兼容版本。

### 额度切换的 v1.1 语义

“额度与刷新”的 `quota_switch_project` 由号池 Router 执行同模型授权卡片间切换；`quota_switch_preview_model` 使用管理员或密钥已保存的原生 `fallbacks` 映射，不猜测预览模型名。先尝试其他同模型卡片，再尝试明确映射的备用模型；没有映射不换模型。

两个开关默认关闭，支持全局和命名配置绑定，保存后由现有对账周期更新内存快照，不需要重新创建部署。旧值不迁移，已存为 true 的值升级后开始执行。只有 HTTP 429 的明确额度耗尽代码（`insufficient_quota`、`quota_exceeded`、`quota_exhausted`、`usage_limit_reached`）接管切换；普通限速和其他故障仍走原策略。

单卡 Key 不能跨卡；备用模型继续通过原生权限检查。工具、有状态续接、签名历史或已经输出的流不重放。CLIProxyAPI 内部两个旧开关及重试仍保持关闭，避免两层重复切换。已知耗尽额度的请求前筛选保持原行为。

验证区分本地模拟上游回归和线上验收；不通过消耗真实账号额度制造测试，不把测试通过写成线上已生效。

## 首次启用

先将包含本功能的提交推送到 GitHub，等待两个镜像构建成功。本机不需要构建 Docker 镜像。将此目录的 `docker-compose.yml`、`releasectl.py` 同步到服务器现有部署目录，保留现有 `.env` 和业务数据

先确认当前项目名和运行 commit，不能因为新增版本管理而更换 Compose 项目名或数据卷名：

```bash
docker inspect -f '{{ index .Config.Labels "com.docker.compose.project" }}' litellm
docker inspect -f '{{.Config.Image}}' litellm
docker inspect -f '{{.Config.Image}}' litellm-account-pool
```

在服务器 `.env` 中增加以下配置。示例路径应替换为实际部署目录，`COMPOSE_PROJECT_NAME` 填上面查到的项目名，令牌可用 `openssl rand -hex 32` 生成。部署目录和备份目录必须使用不同的绝对路径

```dotenv
COMPOSE_PROJECT_NAME=litellm
ACCOUNT_POOL_DEPLOY_DIRECTORY=/opt/litellm
ACCOUNT_POOL_RELEASE_ROOT=/opt/litellm-releases
ACCOUNT_POOL_RELEASE_IMAGE_TAG=包含本功能的提交前10位
ACCOUNT_POOL_RELEASE_TOKEN=独立的随机令牌
ACCOUNT_POOL_RELEASE_DATABASE_BACKUPS=true
```

`ACCOUNT_POOL_RELEASE_IMAGE_TAG` 固定到包含版本管理功能的 Manager 镜像，日常切换不修改它。部署后台使用同一仓库、同一个 Manager 镜像，单独运行在 `release-worker` 容器中，以便业务容器被替换时任务继续完成。它只通过内部 Socket Proxy 管理 Docker，宿主机 8092 仅监听回环地址。它以 root 读取只读部署目录中的 `.env`，备份目录权限设为 0700，配置文件权限为 0600

先启动部署后台，保留两个旧业务容器：

```bash
docker compose pull release-worker release-docker-socket-proxy
docker compose up -d --no-deps release-docker-socket-proxy
docker compose up -d --no-deps release-worker
python3 releasectl.py status
```

首次启动自动备份当前配套镜像，再将本机已有且带完整 commit 标签的历史镜像转为实际归档。历史镜像使用导入时的配置，页面明确标注来源。完整备份会跳过；导入失败保留已成功生成的备份，用 `python3 releasectl.py scan` 重试。仅有 Docker 镜像缓存不会冒充备份文件

确认后台正常后，用下一节的 `deploy` 命令安装新版本。新 LiteLLM 容器会获得版本管理接口需要的内部令牌，页面入口随之可用

数据库快照需要发布器执行 PostgreSQL 导出和临时恢复命令。发布器使用独立 `release-docker-socket-proxy` 和仅内部的 `release-socket` 网络；该代理允许 EXEC、不发布宿主端口，Manager 和 LiteLLM 不加入该网络。Manager 继续连接原来的 `docker-socket-proxy`，保留 EXEC=0。不要把共享代理改成 EXEC=1，也不要给业务进程挂载 Docker socket。已有部署必须保留实际服务、卷、网络和凭据，仅追加独立代理并迁移 worker 的代理地址及网络；授权该管理能力后才能启用

启用数据库备份后，发布会短暂停止 LiteLLM 和 Manager，刷新两库快照并在临时库完成恢复验证，然后才替换业务镜像。`DockerReleaseDatabase.stop` 在停业务前核对数据库身份和 EXEC 权限。备份失败不启动候选镜像，普通升级失败或中断只回退镜像，不回放旧业务数据。显式 `restore_data` 才会恢复数据库，必须单独确认具体快照

受控 OAuth 浏览器升级只允许经过审阅的固定源码摘要和新增会话表、索引组合，还要求 Prisma 和启动证据一致并启用数据库备份。它不放开通用跨 schema 部署。服务器内置浏览器现已退役；历史会话表定义及该固定版本迁移规则保留，避免改变旧版结构指纹和回滚检查。它们不提供浏览器运行能力

## 日常更新

### 搬迁后重新启用

新服务器的程序镜像从 GHCR 拉取，不要求从旧服务器搬镜像。如果不需要旧版本回退，可以保留旧归档不导入，在新架构独立版本目录中为当前运行版本建立备份

原令牌需恢复到 LiteLLM、worker 和维护 CLI，部署路径及 Compose 项目名必须与新机运行状态一致。当前 worker 固定读取 `ACCOUNT_POOL_RELEASE_DEPLOYMENT/docker-compose.yml`；实际配置为 JSON 时，可以在同目录用符号链接指向该文件。备份根目录与部署目录不能嵌套

只改 `.env` 再 `restart` 不会更新容器环境，缺少令牌的 LiteLLM 需按原镜像重建，并恢复其动态账号网络连接。具体备份、最小范围启动、鉴权、归档 hash 验收和跨架构限制见 [迁移手册第 5.5 节](MIGRATION.md#55-网站已经上线但版本管理未启用)

新机仅有当前版本一份备份时，页面回退与删除按钮禁用是正常保护，不代表版本服务故障。备份成功也不代表已验证实际切换，不应为验收随意替换生产业务版本

### 从两个 Compose 项目迁移

如果 LiteLLM 和 Manager 分属不同项目，不能只改 `.env` 中的项目名。先备份两边的实际 Compose 配置、环境变量、数据库、账号认证卷和当前镜像，再生成统一配置。逐项保留运行中的镜像、密钥、命令、端口及挂载，现有数据卷和网络使用明确的 `name` 与 `external: true` 引用，避免生成空卷。两个数据库的服务名应区分，原连接地址需要的网络别名也须保留

统一配置可以放在源码目录之外，避免后续 Git 更新覆盖服务器配置。停止并重建需要更换项目归属的容器，不执行 `down -v` 或卷清理。迁移期间可能中断请求；失败时用保存的原配置恢复原项目。已有账号容器继续保留，业务容器重建后检查到各账号网络的连接及账号 ID

`release-worker` 除内部控制网络外，还需要连接普通桥接网络，Docker 才能正确发布 `127.0.0.1:8092`，供 `releasectl.py` 使用。私有 GHCR 仓库还需要给后台提供 Docker 登录配置，例如只读挂载服务器的 Docker 配置目录；不能把登录凭据放进 Git

迁移成功后检查两个健康接口、号池接口、`/account_pool/releases` 及 `releasectl.py status`，再确认当前版本已生成完整归档。旧部署配置保留作迁移恢复用途，不直接覆盖统一后的配置。新导入的历史镜像使用统一后的运行配置，并不代表已经逐个完成线上回退验证

如果验收发现镜像内的兼容问题，而当前不发布新镜像，可以临时以只读挂载部署补丁，但必须记录基础镜像 commit、补丁文件校验值及恢复方式。当前备份应刷新为包含补丁的配置；后续部署包含修复的新镜像前，从目标部署配置中移除对应挂载，保留补丁文件供旧备份恢复。不要把带补丁的运行状态当成未经修改的原始镜像

### 发布新版本

GitHub Actions 在 `CLIProxyAPI分支` 和 `codex/fix-*` 分支推送时构建两个配套镜像，也支持手动运行。镜像标签是实际提交的前 10 位，镜像内保存完整 commit 标签

两个镜像都发布成功后，在服务器部署目录执行：

```bash
python3 releasectl.py deploy 新提交前10位
```

命令显示目标，等待 5 秒后要求输入 `CONFIRM`。后台拉取两个新镜像，核对 commit，校验或创建当前版本备份，再只替换 LiteLLM 和 Manager。拉取和备份期间旧容器继续运行；归档失败不替换。切换期间请求可能中断，健康检查失败会尝试从原备份恢复

更新后可以将 `.env` 中的 `DEPLOY_TAG` 同步为当前版本，页面以运行镜像身份为准。**后续更新统一使用 `releasectl.py deploy`，不要用普通 `docker compose up -d` 替换这两个业务服务**，后者绕过自动备份，并可能将刚回退的版本覆盖为 `.env` 指定的版本。系统重启由 Docker 的 restart 策略恢复现有容器，不需要重新执行 Compose

部署后台自身的更新应单独安排，确认没有进行中的任务后再更换它的固定镜像标签。旧版业务镜像无法删除或替换这个后台

### 号池设置中的自动更新

管理员在“号池 > 全局设置总览 > 自动更新镜像”开启自动部署并设置检查间隔。默认关闭，默认间隔 5 分钟，允许 5 至 1440 分钟。设置持久化在独立发布器的版本目录，重启不会丢失。启用及修改已启用的设置都需要确认中断风险，并先配置 `ACCOUNT_POOL_RELEASE_DATABASE_BACKUPS=true`

首次使用必须单独升级 `release-worker` 到支持本功能的固定镜像版本，并升级 LiteLLM 页面及代理接口。旧发布器会显示升级提示，不会因打开页面自动获得此功能。自动更新只替换 LiteLLM 和 Manager，不更新发布器自身、数据库容器或账号容器，不拉取服务器源码

发布器读取 GitHub API 中固定仓库 `VVV-345/litellm` 的 `CLIProxyAPI分支` HEAD 及成功的 `publish-deployment-images.yml` 记录，再检查 GHCR 两个配套镜像的当前运行平台。没有完整成功构建时等待下轮，不改用其他分支或较旧提交。GitHub 元数据接口当前按公开仓库读取，服务器须能访问 GitHub API 和 GHCR；私有 GHCR 镜像还需要发布器自己的 Docker 登录配置

比较的是两项运行镜像 ID 与远程 manifest 身份，不只比较标签或 commit。兼容 Docker classic 返回 config 摘要，以及 containerd 镜像存储返回 manifest 摘要。同镜像跳过，不拉取、不停服务；新镜像按检查时固定的 `@sha256` 拉取，并再次验证镜像 ID 与完整 commit。标签在检查后被覆盖也不会换成另一个候选

拉取完成后沿用现有归档、数据库备份及兼容性硬门槛，不放开跨 schema 部署。Compose 启动完成后，额外检查 LiteLLM `/health/readiness` 的数据库连接和 Manager 经鉴权的环境列表接口，并确认运行镜像仍匹配。每个服务的应用就绪检查最多等待约 60 秒。此检查不调用付费模型，也不要求所有账号都有额度；不能代替真实上游请求验收

下载及远程检查失败保留当前服务，等待下轮重试。镜像拉取或替换后的健康检查失败时会尝试恢复旧镜像；自动恢复成功则保留自动更新开关，记录本轮错误并等待下一轮重新检查，恢复失败显示需要人工恢复并暂停自动更新。身份不一致、备份失败、兼容性检查失败或其他无法安全恢复的错误会暂停自动部署，需管理员处理原因后重新开启；不会自动回放旧业务数据。手动发布失败以及手动回退、数据恢复也会暂停自动更新，避免下一轮再次覆盖恢复结果

关闭自动更新会取消尚未执行的自动任务，已经执行的任务会完成或安全恢复。关闭时“立即检查”只发现候选、不部署，手动检查至少间隔一分钟。发布任务与自动检查共用单实例队列，不能并行替换。详情与错误可在“版本与部署日志”查看

停机时间包括停止业务后的两库导出、试还原和新服务启动，失败时还包含恢复旧版所需时间，不能保证固定几秒。镜像检查和下载阶段旧服务继续运行；当前实现没有双副本流量切换，流式请求可能中断。需要先在非生产环境验证备份耗时和恢复，再开启生产自动部署

## 回退与删除

页面选择备份后点击“应用”，等待 5 秒再确认。后台先核对归档 SHA-256，使用 `docker image load` 导入配套镜像，并按归档中的镜像 ID 启动。即使 Docker 缓存或 GHCR 历史镜像已经被清理，完整归档仍可使用。此路径禁止构建和拉取，没有其他镜像来源作为备用

“扫描本机镜像”只列出本项目配套镜像，不拉取、不构建、不导出归档。勾选后点击“备份所选镜像”才创建备份。原 `scan` 命令及首次初始化仅备份当前运行版本，不再无条件导入历史镜像；选择当前版本且已启用数据库备份时仍会暂停业务刷新两库快照

“删除所选备份”会真正删除选中的 `images.tar.gz`、配置、清单、已有数据库快照和索引备注，不清理 Docker 镜像。当前版本和故障恢复引用的备份不能删除。扫描不会自动重新生成已删除的备份，重新勾选备份才会导入

“删除所选本机镜像”清理所选版本的 Docker 镜像及项目内标签，保留可恢复的备份归档。须先备份；确认和执行时检查归档 SHA-256，并核对所有容器（包括已停止容器）及故障恢复引用。被引用、缺失或损坏备份、带其他仓库别名的镜像拒绝删除。不使用强制删除、全机 prune 或数据卷清理，不修改 GHCR 包、Git 提交、认证文件或业务数据库。批量操作逐项执行，失败时已完成项不自动撤销，刷新后可核对剩余项。两类删除均等待 10 秒后明确确认

上述入口需要同步升级 LiteLLM、前端和独立 release-worker；业务镜像更新不自动更新发布器。旧发布器应显示升级提示。镜像删除需要现有发布器 Docker 代理的镜像写权限，不扩大 Manager 的代理权限

每次备份保存配套镜像、完整 commit、镜像 ID/仓库摘要、SHA-256、压缩大小、时间和部署配置。归档及管理索引存入 `ACCOUNT_POOL_RELEASE_ROOT`，与日志目录分开。配置可能包含凭据，不能公开下载、同步到 Git 或随普通日志输出

镜像备份不包含数据库、认证文件和聊天记录。自动应用默认仅接受两个版本的镜像内数据库结构指纹相同；唯一例外是发布器内置并有回归测试的受控向前兼容规则。目前只允许 `TransportPolicy.read_timeout_seconds` 在默认值为 `None` 且持久化省略空值时向前升级，并要求启用数据库备份；一旦显式保存该字段，回退到旧镜像仍会被拦截。其他结构不同或无法读取时停止自动应用，需另行制定数据库备份和兼容升级步骤。数据卷原地保留，镜像回退不会撤销数据写入

## 旧版本没有管理页面时

后台和服务器命令不随业务镜像回退。在服务器部署目录使用：

```bash
python3 releasectl.py status
python3 releasectl.py apply 备份ID
python3 releasectl.py scan
```

`status` 列出当前版本、备份 ID 和最近任务。如果切换与自动恢复都失败，可再次尝试保存的恢复点：

```bash
python3 releasectl.py recover
```

后台重启时会处理未完成的切换：替换阶段的任务尝试恢复原版本，尚未开始的队列任务重新核对运行版本后执行。磁盘损坏或 Docker 不可用时仍可能需要人工修复，可先查看 `docker compose logs release-worker`，不要执行删除业务数据卷的命令

## 从运行版本的代码继续修改

服务器镜像回退不会修改电脑上的 Git 历史。在页面选中目标版本，说明卡片下面提供两组 PowerShell 命令，可直接复制

创建修复分支适合从任意旧版本继续修改：先保存本地修改，再从选中 commit 创建 `codex/fix-提交前缀` 分支，原分支保留。分支名重复时改用新的名称。完成修复并测试后提交，再按需要推送该分支，GitHub 将构建新的 commit 镜像

如果分支起点很旧，尚未包含新的自动构建触发规则，在 GitHub Actions 的 `Publish deployment images` 中选择含本功能的工作流分支，手动运行并将 `source_ref` 填为修复分支名或完整 commit。构建会使用选中源码的真实提交号作为标签和 revision，不会误记成工作流所在分支的提交号

`git revert` 适合在当前分支撤销目标 commit 之后的改动，产生新的撤销提交。命令先检查工作区、祖先关系及合并提交，显示准备撤销的范围，并要求输入 `REVERT`。发生冲突时解决后继续，或 `git revert --abort` 取消。已推送的提交不通过 reset 或强制推送删除，因此上一版本也推荐用分支或 revert

以上命令不自动 push，不自动切换服务器版本。说明内容可以手写修改，命令中的目标 commit 始终根据选中的版本生成

## 本次 v1.3 发布目标

本次按用户要求将 `deploy/VERSION` 设为 `v1.3`。已有成功标签仍在较低系列时，下一次普通构建使用 `v1.3`，失败重试不占号；只有配套镜像发布成功才写入不可变成功标签。成功后的后续构建依次使用 `v1.3.1`、`v1.3.2`。此文件表示目标版本，不表示镜像已经构建成功，也不自动部署服务器

SSE 心跳设置支持继承、关闭及大于 0 到 300 秒的间隔。原生模型组如果混用号池和普通部署，在选定部署前的等待阶段仍沿用全局心跳；实际选择号池后使用号池设置。不为此改变普通原生部署的心跳策略

## ISP 手动检测

`v1.3` 候选加入 ISP 单个和全部检测，展示实际出口 IP、近似国家/地区和城市、运营商、请求延迟、连通状态及检测时间。Manager 经所选 ISP 访问 `https://api.ipify.org?format=json` 测量完整请求耗时，再向 `https://ipwho.is/<出口 IP>` 查询位置；不发送代理凭据。第三方服务可能限流或不可用，位置失败时保留出口 IP 和延迟，不据此更改代理配置。全部检测按顺序执行，Manager 同时最多处理 3 个检测请求，每个请求总上限 12 秒。结果仅保存在当前用户的界面查询缓存，不写数据库

验收入口：号池页面的 ISP 代理卡片，点击“检测”或“检测全部 ISP”。镜像发布成功不等于服务器已部署，仍沿用既有版本和发布门禁
